# gtm-loop — Self-Improving GTM Agent

**MadeThis Bounty: Build a Self-Improving GTM Agent** · AI Builder Day

Loop owns one end-to-end GTM loop — signal → opportunity → proposed action →
approval/autopilot execution → observed outcome → behavior change — with
persistent memory, guardrails, and an explainable activity trail.

## 1. What Loop is

Most AI GTM tools stop at a lead list or copy. Loop closes the loop:

- **Propose mode** — every action lands as a decision card (what / why /
  evidence / guardrails / what it learned / what's next). Approve, reject with
  a reason, or edit. Nothing executes without a human decision.
- **Autopilot mode** — acts within user-defined scope, budgets, frequency
  limits and guardrails. Irreversible, external, or high-cost actions always
  require approval.
- **Self-improving** — rejections/edits/outcomes feed a policy engine and
  Thompson-sampled experiment stats. Feedback *changes the next action*, not
  just a note. (Proof: behavior-change tests in `tests/test_learn.py`.)
- **Trust** — append-only activity trail, decision traces, pause/stop controls.
- **Fully local** — deterministic synthetic data, simulated sends, zero network
  dependencies. The demo runs offline.

## 2. Architecture — the six-stage loop

```
        ┌─────────────────────────────────────────────────────────┐
        │                       gtm-loop                          │
        │                                                         │
 SENSE  │  scan() → signals → qualify() → opportunities           │
   │    │                                                         │
 DECIDE │  NBAM (Thompson) → choose_next_best_action              │
   │    │  generate_draft() under current policy state            │
   │    │                                                         │
PROPOSE │  build_decision_card() → approval queue (PROPOSED)      │
   │    │  Propose mode: human decides | Autopilot: scoped auto    │
   │    │                                                         │
   ACT  │  execute() → SENT + activity trail entry                │
   │    │                                                         │
OBSERVE │  record_outcome() → reply/meeting/no-response           │
   │    │                                                         │
 LEARN  │  apply_feedback() → policy deltas                       │
   │    │  update_variant_stats() → Thompson priors               │
   │    │  update_warm_graph() → relationship memory              │
   └────┴─────────────────────────────────────────────────────────┘
```

Each stage is an independent module under `src/engine/` with a stable pydantic
contract (`src/domain/models.py`) and its own test file. The heartbeat
(`src/api/main.py`) drives the loop on a timer; the API exposes the decision
queue and controls.

## 3. Models

- **Template engine under policy state** — drafts are generated by rendering
  playbook variant templates with personalization. The current policy
  (brevity_weight, tone_assertiveness, personalization_depth) steers template
  selection and content. No LLM key required.
- **Optional LLM adapter** — `src/engine/generate.py` supports an LLM backend
  via `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` env vars. Documented, not
  required; the demo stays offline.
- **Thompson sampling** — `choose_next_best_action` in `src/engine/plan.py`
  picks variants by sampling Beta posteriors from stored outcome stats,
  balancing exploration and exploitation.
- **Feedback → policy map** — `apply_feedback` in `src/engine/learn.py`
  classifies rejection reasons (e.g. `too_salesy` → tone_assertiveness↓,
  `too_long` → brevity_weight↑) and edit deltas into policy version bumps.

## 4. Data & integrations

- **Synthetic local feed** — `scan()` in `src/engine/sense.py` generates
  deterministic signals from seeded companies (funding, hiring, product,
  pricing, content) with configurable probabilities.
- **SQLite schema** — versioned migrations in `src/store/db.py`. Tables:
  companies, contacts, signals, opportunities, actions, outcomes, activity,
  experiments (variants), policies, warm_edges, memory_kv.
- **Channel adapters** — email and LinkedIn are simulated by default
  (`SIMULATION_MODE=on`). No external paths in v1.

## 5. Permissions & guardrails

- **Propose / Autopilot modes** — mode + pause/stop control state via
  `src/engine/permission.py`; scope persisted in `memory_kv`.
- **Action-class matrix** — permission checks classify actions
  (IRREVERSIBLE, EXTERNAL, HIGH_COST, BULK) and require approval for
  high-risk classes even in autopilot.
- **Budgets & caps** — daily/weekly send budgets, per-contact frequency caps,
  follow-up limits, cost thresholds (`src/config.py`).
- **Kill switch** — pause / stop / resume endpoints.
- **SIMULATION_MODE** — gates real external sends; on by default.

## 6. How feedback changes future actions

Three mechanisms, each with a before/after proof test:

1. **Rejection reasons** → policy delta. Reject `too_salesy` and the next
   draft for the same segment is measurably softer (tone_assertiveness↓).
   Test: `test_reject_softer_next_draft`.
2. **Edits** → policy delta. Edit with warmer tone → tone_assertiveness nudges.
   Test: `test_edit_produces_policy_delta`.
3. **Outcomes** → variant stats + warm graph. A meeting booked strengthens the
   relationship edge; a no-response shifts Thompson priors away from that
   variant. Tests: `test_outcome_updates_variant_stats`,
   `test_positive_outcome_strengthens_warm_edge`.

## 7. Demo script (3–5 minutes)

See [PLAN.md §10](PLAN.md) for the full 8-scene walkthrough. Run it with:

```bash
python seed_data.py   # clean deterministic world
python demo.py        # prints scene-by-scene narration
python run.py         # start API + UI at http://localhost:8000
```

Scenes: heartbeat → proposals → edit+approve → reject with reason →
autopilot → outcomes → learning cycle (before/after) → trust close.

## 8. Run instructions

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest -q                     # 153 tests
python seed_data.py           # build a deterministic synthetic world
python run.py                 # start the API on http://localhost:8000
cd frontend && npm install && npm run dev   # optional React UI
```

Fully offline. Optional LLM env vars (`LLM_BASE_URL`, `LLM_API_KEY`,
`LLM_MODEL`) enable the LLM adapter.

**API authentication (optional):** set `GTM_API_KEY` to require the key on all
`/api/v1` endpoints via the `X-API-Key` header. Unset (default) leaves the API
open for local development. The server binds to `127.0.0.1` by default; set
`GTM_HOST=0.0.0.0` to expose it (only recommended with `GTM_API_KEY` set).

**Trust & audit (compliance artifact):** every action is fully explainable and
replayable. `GET /api/v1/audit/export` returns the complete trail — every
action with its `decision_trace`, guardrail results, outcomes, human decisions
with reasons, and policy version at the time — enough to reconstruct any
moment in history. `GET /api/v1/audit/explain/{action_id}` shows the raw trace
+ exact template + policy snapshot for one action. `GET /api/v1/audit/pii`
reports any drafted bodies/subjects that hit `PII_PATTERNS` or
`BANNED_PHRASES`, keyed by action ID. The same patterns run as a pre-send
guardrail in `permission.guardrail_checks`.

## Repository layout

```
PLAN.md              # full 1-day sprint plan (tasks, schedule, criteria matrix)
seed_data.py         # deterministic synthetic world + playbook variants
demo.py              # scripted 8-scene demo driver
src/config.py        # budgets, caps, guardrails, thresholds, scoring weights
src/domain/          # pydantic contracts + enums (signal, action, outcome, ...)
src/store/           # SQLite schema + versioned migrations + connection helpers
src/engine/          # sense → plan → generate → propose → permission → execute → observe → learn
src/api/             # FastAPI app, approval queue routes, control, activity trail
frontend/            # React + TypeScript + Vite UI (shadcn/ui components)
tests/               # 153 tests (schema, qualify, plan, permission, learn, e2e demo)
```

**Frontend UI:** built on **shadcn/ui** — composable primitives live in
`frontend/src/components/ui/` (built on Radix + class-variance-authority +
Tailwind), with feature components in `frontend/src/components/` composing
them. All feature components use the primitives; no raw HTML form elements
outside `ui/`. Add new components via the shadcn CLI
(`npx shadcn@latest add <name>`) inside `frontend/`.
